## 一、全自动创作逻辑优化（7 项）

### 1. DAG 并行执行（核心架构改造）

**文件**：`server/src/services/autoPipeline/runner.ts`（完全重写）

**改造前**：10 阶段严格串行执行
```
novel → episodes → script → characters → scenes → shots → keyframes → video → audio → export
```

**改造后**：基于依赖关系的 DAG 并行执行
```
novel → episodes → script → [characters ‖ scenes] → shots → [keyframes ‖ audio] → video → export
```

**并行组分析**：
- `[characters ‖ scenes]`：两个阶段都只依赖 script 完成，互不依赖，可并行
- `[keyframes ‖ audio]`：关键帧生成和 TTS 配音都只依赖 shots，互不依赖，可并行
- `video` 依赖 keyframes（需要首帧/尾帧），单独执行
- `export` 依赖 video + audio（两者都已完成）

**效率提升**：假设 characters 和 scenes 各需 30 秒，keyframes 需 10 分钟，audio 需 2 分钟，并行后节省约 **12.5 分钟**（30s + 120s + 关键帧与配音重叠的 2 分钟）。

**实现细节**：
- 新增 `EXECUTION_PLAN` 常量定义执行步（单阶段字符串或并行组数组）
- 新增 `executeSingleStage()` 封装单阶段执行（幂等跳过、取消检查、耗时统计、错误捕获）
- 新增 `executeStep()` 统一处理单阶段和并行组
- 并行组内所有阶段独立执行，任一失败标记整个步失败并返回第一个错误

### 2. 统一 AI 调用重试机制

**文件**：`server/src/services/autoPipeline/helpers.ts`（新增 `withRetry`）

**问题**：text 阶段（episodes/characters/scenes/shots）的 AI 调用失败直接中断整个流水线，没有任何重试。网络波动、API 临时故障、限流等偶发错误会导致整个流水线失败。

**解决方案**：新增 `withRetry<T>()` 统一重试包装器：
- **默认 3 次重试**，指数退避（2s → 4s → 8s）
- **限流(429)特殊处理**：退避基数提升到 10s（10s → 20s → 40s）
- **不可恢复错误立即抛出**：400 参数错误、JSON 解析失败等不浪费重试额度
- **每次重试记录日志**：便于排查问题

**已接入重试的阶段**：
| 阶段 | AI 调用 | 重试次数 |
|------|---------|---------|
| episodes | 剧集拆分 | 3 次 |
| characters | 角色提取 | 3 次 |
| characters | 造型分析 | 2 次 |
| scenes | 场景提取 | 3 次 |
| shots | 分镜生成 | 3 次 |

**注**：keyframes 阶段已有自定义限流重试（6次，15s递增），video 阶段已有 3 次重试，均保留原有逻辑。

### 3. 断点恢复修复（resumeFromStage 死代码）

**文件**：`server/src/services/autoPipeline/runner.ts`

**问题**：`resume()` 函数设置了 `task.resumeFromStage = task.currentStage`，但 `runPipeline()` 从未使用该字段，恢复时总是从 novel 开始遍历（虽然幂等跳过会跳过已完成阶段，但 `resumeFromStage` 是死代码）。

**修复**：
- 新增 `findResumeStepIndex()` 函数，根据 `resumeFromStage` 定位到 DAG 中的执行步索引
- `runPipeline()` 从 `startStepIdx` 开始执行，跳过之前的步
- 之前步的幂等跳过仍会自动处理（双保险）

---

### 4. 总体进度百分比

**文件**：`helpers.ts`（新增 `calculatePipelineProgress`）、`types.ts`（新增 `progressPercent` 字段）、`runner.ts`、`taskStore.ts`

**问题**：全自动运行时只有文字描述的阶段进度（如"生成中 5/10"），没有总体百分比，前端无法显示进度条。

**解决方案**：
- 新增 `progressPercent: number` 字段到 `AutoPipelineTask`
- `calculatePipelineProgress()` 根据已完成阶段数计算百分比，当前进行中阶段计 50%
- 每个阶段完成/跳过时更新 `progressPercent` 并持久化
- 从数据库恢复任务时自动反推 `progressPercent`
- 任务完成时设为 100%

---

### 5. 剧本分析缓存竞态修复

**文件**：`server/src/services/autoPipeline/state.ts`、`helpers.ts`

**问题**：characters 和 scenes 并行执行时，两者都调用 `getOrCreateScriptAnalysis()`。由于缓存检查和 AI 分析不是原子操作，两个阶段可能同时触发 AI 分析，导致重复消耗额度。

**修复**：
- 新增 `scriptAnalysisInFlight: Map<string, Promise>` 进行中锁
- 第一个调用触发 AI 分析并将 Promise 存入 Map
- 后续调用发现 in-flight Promise 后直接 await 同一个结果
- 分析完成（成功或失败）后清理 in-flight 锁

---

### 6. 逐镜/逐帧进度持久化

**文件**：`stages/audio.ts`、`stages/keyframes.ts`

**问题**：audio 阶段只在全部完成后更新一次进度；keyframes 阶段更新进度字符串但不调用 `saveTask` 持久化。前端轮询时看不到实时进度。

**修复**：
- **audio.ts**：每镜生成成功/失败后都调用 `saveTask(db, task)`，进度格式 `生成中 X/Y（失败Z）`
- **keyframes.ts**：每帧生成后调用 `saveTask(db, task)`，进度格式 `生成中 X 帧，跳过 Y`

---

### 7. 阶段耗时统计

**文件**：`types.ts`（新增 `stageStats`）、`runner.ts`

**新增**：`stageStats: Record<string, { retries: number; durationMs: number }>`
- 每个阶段完成后记录耗时（毫秒）
- 记录重试次数（预留字段，后续可接入 withRetry 的重试计数）
- 用于后续性能分析和优化

## 二、半自动创作逻辑优化（5 项）

### 8. 批量视频生成时长修复

**文件**：`src/components/StageDirector/BatchToolbar.tsx`

**问题**：`handleBatchGenerateVideos` 硬编码 `duration: 5`，无视用户在项目配置栏（ProjectConfigBar）设置的单镜时长（5-60 秒阶梯）。

**修复**：
- 新增 `resolveProjectShotDuration()` 异步函数
- 优先读取 `useProjectStore.currentProject.default_shot_duration`（校验 5-60 范围）
- store 缺失时通过 `apiClient.get('/projects/{id}')` 兜底查询
- 都不可用时回退 5 秒（与后端 `shots.ts` 语义一致）

---

### 9. 批量首帧跳过已存在

**文件**：`src/components/StageDirector/BatchToolbar.tsx`

**问题**：批量生成首帧时对所有镜头都提交，后端 `batchGenerateKeyframes` 对已有首帧的镜头是"先生成新帧、成功后删旧帧"，重复点击会重新生成已有首帧并重复消耗额度。

**修复**：
- 新增 `fetchShotsWithFirstFrame()` 函数，分批（每批 8 个）并行查询每镜的关键帧
- 收集已有 `frame_type === 'first' && image_url` 的镜头 ID
- 批量生成前过滤出 `pendingShots`（缺首帧的），通过 `shotIds` 参数只提交这些镜头
- 全部已有首帧时直接提示"全部 N 个镜头已有首帧，无需重新生成"
- 进度条 total 改用 `pendingShots.length`

---

### 10. 视频生成超时动态化

**文件**：`src/components/StageDirector/ShotCard.tsx`

**问题**：轮询 effect 硬编码 `TIMEOUT_MS = 10 * 60 * 1000`（10 分钟）。本地 ComfyUI 渲染单镜 20-40 分钟且按队列渲染，会被误判超时，导致用户以为失败但实际还在渲染。

**修复**：
- 新增 `pollingIsLocalComfy` 状态
- 创建视频任务时检测模型：`provider.includes('comfy') || modelName.includes('flf2v')`
- 本地 ComfyUI 模型 → 24 小时超时（与后端 `video.ts` 第 387-389 行一致）
- 云端模型 → 10 分钟超时
- `handleGenerateVideo` 和 `handleGenerateFLF2V` 都设置该状态
- 删除视频时重置该状态

---

### 11. 手动改分镜后下游过期警告

**文件**：`src/components/StageDirector/ShotCard.tsx`

**问题**：用户在剧本页/分镜表手动修改分镜后，已生成的关键帧和视频仍然基于旧分镜，但界面没有任何提示，用户可能不知道需要重新生成。

**修复**：
- 新增 `isDownstreamStale`（useMemo）
- 逻辑：`shot.updated_at` 晚于任一关键帧或视频的 `created_at` → 标记为过期
- 在卡片摘要行显示 `⚠ 分镜已修改，建议重新生成` 警告徽章

**可靠性验证**：已核实 `ShotDAO.update` 仅在 5 处调用——手动编辑分镜（PUT /shots/:id）、分镜生成/重排/加料重构；**生成关键帧/视频不会 touch shots.updated_at**，因此不会误报。

---

### 12. 场景图片生成状态修复

**文件**：`src/components/StageAssets/StageAssets.tsx`

**问题**：第 48 行 `const [generatingSceneImages] = useState<Set<string>>(new Set())` 只声明了 getter 没有 setter，永远是空 Set。场景卡片上的"生成中"状态（`isGenerating = generatingSceneImages.has(scene.id)`）永不显示。

**修复**：
- 补全解构：`const [generatingSceneImages, setGeneratingSceneImages] = useState<Set<string>>(new Set())`
- `handleGenerateSceneImage` 开始时 `add(sceneId)`
- `finally` 中 `delete(sceneId)`
- 使用局部变量 `sceneId` 捕获场景 ID，避免异步闭包问题

## 六、后续可优化方向（建议）

1. **多剧集支持**：当前所有 stage 只处理 `episodes[0]`，可扩展为遍历所有剧集
2. **阶段级模型配置**：允许用户为每个阶段单独配置模型（当前统一用 getFirstModel）
3. **过期状态下沉到后端**：将分镜修改后下游过期检测放到 readiness 接口统一返回
4. **批量视频过期检测**：批量生成视频时对过期镜头同样提示
5. **结构化日志**：将 console.log 替换为结构化日志系统，便于生产环境排查
6. **临时文件清理**：视频重试时的 failed 记录和临时文件定期清理
